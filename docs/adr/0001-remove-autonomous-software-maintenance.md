# 移除旧自主维护机制；由受监督 Admin 修复协议逐步替代

状态：历史决定保留；“打包应用的修复只能在产品之外进行”已由 Admin 自动修复目标取代。新的自修复交付仍在实施，不能据此宣称版本切换或回滚已完成。

## 原决定

LoopWork 移除 Maintenance Runner、Maintenance Agent、修复队列、隔离 worktree patch、自动落地和自主维护页面，仅保留结构化运行事件与日志。升级 migration 直接删除自主软件维护的全部表和历史数据，不保留兼容读取。打包应用无法可靠修改并更新自身安装源码，而独立维护进程还会增加 Windows 更新时的进程残留与安装目录锁定风险；故障诊断和源码修复应由安装包之外的开发工作流完成。

## 新约束与迁移

不复活旧表、旧 Maintenance Runner 或直接仲裁完成 Dev/Test 的能力。改由独立 Management DB、受用户意图与代次约束的 Admin Controller、RepairCase 和独立验证执行负责修复。重复 Agent 故障升级方法，不因耗尽固定次数转人工。

LoopWork 自身故障必须定位实际安装版本的源码，在隔离工作区修复、测试并构建。切换由外部控制执行，失败回退已知可用版本，数据库必须有代码回滚兼容方案。原始失败与验收保留，正常业务实际恢复后才关闭修复记录。

桌面发行包同时保存彼此独立的业务镜像 `app-server` 与管理镜像 `management-bootstrap`，打包后逐字节验证二者来源一致。Electron 主进程从管理镜像加载外部恢复能力，把业务镜像只作为待验证输入；因此业务镜像在能力启动前损坏时，管理入口仍可运行。独立管理镜像不是修复结论，也不能替代不同源码的故障镜像；只有只读源码归档、版本和 Build ID 与完整验证的管理 artifact 精确对应时，才可用它恢复源码。

已落地源码归档、冻结源码构建、相同源码候选复用、独立验证和外部切换入口，具体格式、边界与仍待真实模型/整夜验收的要求见 [Harness 自修复](../harness-self-repair.md)。发行更新器不等同于这个本地自动修复闭环。
