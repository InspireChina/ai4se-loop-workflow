# Harness 自修复：准确源码与候选版本

这是 Admin 修复链的一部分，不是发行下载器，也不是旧 Maintenance Runner 的恢复。目前已有准确源码、隔离构建及真正的外部原生版本切换/失败回滚/数据库读者适配器；这些受控产物与进程验收不等于 Admin 已自主修复源码，也不等于原业务已恢复。真实业务修复闭环仍待完成。

## 准确源码

`npm run build` 通过 `scripts/build-harness.mjs` 收集当前实际文件，包括未提交改动，而不是假设 Git HEAD 等于安装版本。快照包含 `app/src/scripts/desktop`、测试、两套数据库迁移和命令链，以及 package/lock/TypeScript/Next 配置。源码标识为排序后的路径、内容 SHA-256 与可执行位的整体 SHA-256。

只选择构建所需源码目录与文件类型，不收集工作区 `.env*`、用户数据库、日志、临时目录、安装输出、依赖目录和命名的私钥文件。符号链接、硬链接、跨平台不安全路径、超限文件拒绝打包。这个规则不识别写进普通源码里的秘密；发行前仍须检查源码内容，不应把凭据写进代码。

构建在新建的私有临时目录中还原冻结源码，并复制独立的已安装依赖树。Next 在该目录编译；构建后再次检查冻结源码及当前工作区。成功结果绑定实际 `.next/BUILD_ID`，记录构建 Node/平台/架构。`next-env.d.ts` 是 Next 自动生成文件，不作为稳定输入。源码变化、编译失败或上次构建的来源回执缺失时，不能打包候选版本。

这不是安全容器：恶意构建脚本、第三方依赖和同用户的恶意进程仍需额外隔离。来源散列也不是发行签名；不能以它证明不可信安装包的真实性。

## 安装包与外部还原

Desktop runtime 携带 `harness-source.json.gz` 与 `harness-tools/`。源码和测试存在压缩数据中，不进入运行时模块解析；原有“不得安装测试执行代码”门禁保持有效。打包再次检查来源与 Build ID，拒绝旧 Next 产物配上新 Runner 源码。

桌面发行包把同一已验证 runtime 分别复制为 `app-server` 与 `management-bootstrap`，再对两份完整安装字节和 sourceId/version 做独立复验。Electron 主进程始终从 `management-bootstrap` 加载外部 Root/管理能力，把 `app-server` 作为可能已经损坏的业务安装输入。独立服务定义也可显式传入 `--management-root`。因此首次业务能力启动前 `app-server` 的 Runner/Next 字节损坏时，管理入口仍可创建同一个 runtime RepairCase；这不是让损坏镜像执行诊断代码。

损坏镜像仍可通过只读、逐文件身份稳定的源码绑定读取归档、package 版本、Build ID 和声明 artifactId；该读取刻意不校验其余可执行字节，不能证明镜像健康。只有这些源码事实与一个完整重验、内容寻址的管理 artifact 精确匹配，观察才保存 `sourceArtifact/sourceEquivalence` 并允许还原。不同源码的管理镜像只用于继续诊断，不能冒充故障版本源码；源码归档本身损坏时也不会猜测当前 checkout。

用独立 Node 运行以下命令，还原到安装目录之外一个不存在的新目录：

```sh
node /absolute/app-server/harness-tools/harness-source-cli.mjs \
  --runtime-root /absolute/app-server \
  --workspace /absolute/private/repair-source-new
```

CLI 在写文件前验证归档全部路径、内容、排序、整体身份及安装版本/Build ID。已有工作区和安装目录内的目的地拒绝操作。它没有业务数据库导入，不修改任务状态，不启动业务 Loop。

还原后应根据 lock 安装适配实际构建环境的依赖，再执行测试、独立 TypeScript 和候选构建。源码归档不携带 `node_modules` 或 Electron 原生二进制；候选必须重新选择正确 ABI。

## Admin 管理命令准备源码

原生 Admin 会话可通过已有受监督、带版本及幂等校验的命令通道请求还原原始故障版本：

```sh
loop-admin status
loop-admin harness workspace --key original-source \
  --observation-id <当前Case原始runtime故障的ID> \
  --reason "还原原始故障版本，在隔离目录调查"
loop-admin status
```

只有当前 Case 的原始 runtime artifact 来源可用；调用者不能传入任意安装路径、源码版本或目标目录。必须等待 `status.actions` 中对应动作 `completed` 且 `result.phase=prepared`，再读取 `workspaceRoot`。管理端在独立原生能力子进程中核对内容寻址缓存、归档散列、源版本和实际 Build ID，创建此前不存在的私有目录。子进程使用稳定 Root 镜像，不要求故障镜像可执行，也不导入业务数据库；因此业务库或所选业务镜像损坏不会阻断源码还原。

停止、监督权失效、Admin 已终止提交会中止还原；部分目录与原始故障记录保留，不能重用或记为成功。`prepared` 仅表示源码已还原，`liveWorkspacePermission=false`；它不是业务资源接管、构建验证、更新授权、Dev/Test 完成或 RepairCase 修复成功。原始 runtime 故障的独立验证及更新交接还需接入完整管理协议。

## Admin 候选构建

在本轮已准备目录完成实际源码修复后，可以请求固定构建链：

```sh
loop-admin harness build --key candidate-1 --workspace-key original-source \
  --reason "实际修复后，测试并构建隔离候选"
loop-admin status
```

调用者只引用本轮已完成的源码动作 key，不能传入任意路径、命令、构建工具或伪造收据。宿主再次检查原故障来源与本轮授权，在新的私有目录冻结当前实际源码，并通过本机 Node 24/npm 安装 lock 对应依赖，依次执行完整测试、独立 TypeScript、Next 和桌面构建。测试不继承编译数据库路径；其初始化为每个进程重新建立数据库和工作区。缺少可用 Node/npm、阶段失败、日志失败、源码发生变化、停止或失权均不能登记成功；失败日志与私有目录保留。

构建使用独立、受登记的原生进程通道，最多 20 分钟。已确认实际身份且监督代次和意图相同的构建与短诊断可以并行；未知分配或旧代次仍阻止并行。停止、更新和前代清理覆盖两条通道及其实际退出屏障；不会借用普通 Agent 槽位或仅凭子进程 close 释放资源。

成功的 `status.actions` 返回 `phase=candidate-built`、实际内容寻址 `candidate`、源码身份、分阶段收据和 `logFile`。`independentVerificationRequired=true`：完整测试与构建通过不等于原 runtime 故障修复通过；此动作不会选择候选、更新运行版本、完成 Dev/Test 或关闭 Case。还必须由独立验证覆盖全部原始故障／验收、校验实际执行版本，并经外部更新与普通业务恢复观察。

相同修复源码跨轮再次请求构建时，宿主可复用先前的实际候选，但门禁只接受已经物理结束的 investigation、原始（非复用链）五阶段成功收据、真实 toolchain 元数据、准确原 runtime/source 授权和未损坏的内容寻址字节。controlled fixture、额外/缺失收据、不同 sourceId、损坏目录或复用链均拒绝；拒绝后执行当前轮真实构建，而不是记成功。复用仍为当前 attempt 创建独立冻结源码，结果保存 `reusedFrom`，当前轮必须重新独立覆盖全部原故障、执行外部切换与业务恢复观察；旧 Case 的验收结论不会继承。

## 原始 runtime 独立验证与外部切换请求

Harness 修复提交的 `repairVersion` 必须是本轮真实构建返回的完整 `result.candidate.artifactId`；`repairEvidenceKeys` 包含该构建动作的实际 key。应用版本号、Git 提交、源码 hash、修复者自拟版本或总结不能代替候选身份。宿主要求完整五阶段成功收据，并绑定原故障准确源码和本轮管理授权。

独立验证保留所有原始 runtime 故障事实；混合业务原始记录时仍保留完整原验收，不虚构 task 或契约。独立准备进程生成冻结检查，但不产生通过结论；另一个物理验证进程执行实际候选的编译入口，并前后读取候选真实字节身份。工作目录是候选镜像，数据目录是本轮私有验证目录，不继承业务数据库和运行意图覆盖。冻结源码、内容寻址候选、软链接/别名、实际构建退出屏障和监督代次均重新检查。缺少原始复现输入必须失败，不能用 boot、构建成功或 hash 相同替代原始故障重放。

只有已完成且进程退出的独立验证可进入 `observing`。原生管理宿主再检查冻结源码和真实候选字节、完整原目标覆盖、当前原安装选择以及全部管理/能力进程退出，随后向独立外部更新控制器提交确定性请求，进入更新静默。Agent 命令不能传入任意切换路径或自行授权。回滚的同一请求不会重新提交，外部失败记录与原始故障一并保留，重新排队调查；中止属于中性取消记录，不增添原始失败目标或错误次数。用户停止仍禁止请求及自动调查，重新启动后才可继续未完成修复。

此入口只证明候选获准交给外部切换协议。启动健康、切换完成和独立验证都不能关闭 Case；仍需实际新业务执行推进证明。非 Harness 环境故障的现有镜像验证和更广泛的构建前 runtime 独立诊断尚未完整覆盖，不能把本节能力泛化为所有 runtime 故障已自动修复。

## 物理交还收据

切换请求与“旧普通宿主／更新分配／活动 CLI 的身份集合、宿主序号”在同一管理事务保存。成功切换后的普通宿主必须是之后新分配、实际版本匹配且 CLI 协议已认证的宿主，不能复用切换前 ready 标志。Root 独立核对冻结源码和候选实际字节、新宿主 PID／启动身份／进程组，以及被捕获的旧宿主、持有式更新和脱离宿主组的 CLI 实际退出；数据库状态标为 exited 本身不是原生进程组消失证明。未知身份或无法核对均拒绝交还，不杀不明进程。Windows 需要原生容器证明；尚无完整生产证据时不能伪造通用通过。

物理交还证据由独立管理库保存，不写业务数据库、不完成工作项、不关闭 Case。同一实际宿主的检查幂等；换成另一个实际普通宿主时追加新的交还代次，原证据不可改写，管理重开可继续读取。交还校验真实失败保存原始来源和失败事实，返回自动调查；尚没有新普通宿主时返回等待，不凭空记录修复完成。用户停止、更新静默和监督变化仍阻止提交。

切换回滚或物理交还失败留下宿主确认的独立失败身份，恢复策略将其计入持久化升级预算；不能因为前一轮独立验证确实通过就永远以“第一次调查”重复。通过的验证收据仍然通过，不伪造失败 execution；中性取消和重复同一失败身份不重复消耗预算。

原业务新执行的实际运行版本、结果应用和流程推进必须与这些交还收据衔接后，才能关闭 runtime Case。原生只读观察和管理关闭事务现已衔接；物理交还记录本身仍不等于原业务已经恢复。

## 原业务推进的只读检查

`captureRuntimeBusinessBaselineInDb` 与 `findRuntimeBusinessProgressCandidatesInDb` 提供只读证据核心。基线接到原生外部切换的 stopping 阶段并保存至独立管理库，推进候选由稳定 Root 的独立能力读取，再经管理关闭事务。基线在更新静默、旧写入进程实际退出后冻结，读取前后重新校验 Root/管理监督、实际更新阶段和独立验证来源；不得在旧业务继续运行时提前拍照，也不得在新候选开始派发后补拍。绑定 Case、独立验证、更新 ID、完整候选身份及原始故障时间边界，保存原工作项 revision、epoch 和旧 execution 集合。时间或 schema 无效直接报错，不伪造空负载。故障后的取消或 supersession 不能抹掉原需求的恢复义务。

`runtime-business-baseline` 通过稳定 Root 镜像的独立受管能力进程执行，不加载业务 bootstrap/迁移，不占普通 Agent 槽位，只打开实际业务库的 readonly/fileMustExist 连接。旧宿主、更新分配及被捕获活动 CLI 的实际进程组仍需为空；ledger 的 exited 标志不能代替此检查。候选源码和完整候选字节也重新检查。保存的基线不可重拍覆盖；提交后崩溃可读取原基线继续。只有确实 ENOENT 才保存 absent 且零任务，schema/权限/损坏/别名错误不能降级为空。此能力不修改原业务数据，不关闭 Case。

更新静默通过 suspendCapabilities 停止写能力和构建能力，保留这项 Root 受控只读采集；用户 STOP、监督失效和宿主关闭仍通过 stopCapabilities 终止全部能力及实际进程组。读取失败进入受监督的回滚路径，不能先启动候选再补拍；已验证修复的候选 startHeld 也检查管理库中的基线，不允许缺失基线跳过新门禁。普通发行更新不虚构 RepairCase/原任务，沿用原更新协议。Windows 有旧进程时仍需要真实原生容器证据，当前不能凭 ledger 放行。

推进候选只读取普通 Agent 的实际完成事件、`applied` execution、`applied/advanced` result 以及当前工作项 epoch；旧结果、无关新需求、仲裁/人工完成、暂停、删除、未解决介入或未退出的 execution 进程均不通过。执行还必须关联已交还候选宿主下登记并退出的 CLI；不同宿主代次各自保留来源，一条原需求有一次正常推进即可，不要求提前完成所有未来阶段或绕过人工结卡。

这些返回值刻意命名为 candidate，不是修复完成收据。`runtime-business-progress` 仅由当前 Root 的私有受管能力进程执行，使用 Root 镜像而非可能损坏的业务镜像，不加载业务 bootstrap/迁移，不提供 Agent 参数伪造完成。正常运行、完整独立验证、当前新宿主实际身份、完整候选字节、历史交还来源和对应 CLI 实际进程组为空全部重新校验；Root 自己不是普通 CLI 所有者。 unrelated CLI 的新登记不使已退出执行的来源失效，但版本、宿主、旧来源或需求结果变更必须重读。

每条原需求的新执行证据写入管理库 append-only 历史。部分推进不能关闭；只有冻结的全部原需求当前都具备同一批已经物理校验、已持久化的正常完成证据，且最终一致只读查询仍精确匹配，管理事务才保存闭合清单并关闭 Case。暂停、回退、介入、故障代次或监督变更阻止迟到关闭；重复关闭只读取当前验证代次的历史清单，不再次派发。复发继续同一 Case 历史，新故障使旧代次无权关闭。真实读取/物理证明错误保存标准 runtime 事实和每验证轮唯一恢复预算 ID，继续自动调查，而不是完成 Dev/Test；STOP 不计为失败。

基线的时间范围由本轮全部已独立验证原故障的实际持久化时间生成：最早故障决定哪些完成/取消是历史，最晚故障决定哪些后来创建的需求已经受影响。不能沿用 Case 首次创建时间漏掉复发时的新需求，也不能以最后一次故障为准删掉期间已经完成或取消的恢复义务。时间范围保存后不可更改；旧基线不重拍覆盖。

冻结前已经发生原生回退时，只沿实际 superseded_by_item_id 链找到当前头，不取 MAX(revision) 或另一工作项。每步必须同 task/work_key/kind/story_index、revision 严格递增且无缺失/循环。基线保存原 predecessor IDs/revisions、当前头的契约身份和整条链已有 execution 集合，重复到同一头去重但不能丢失较长原链。旧 schema 没有这些列时不猜测 lineage。后续普通结果还要匹配被冻结头的契约身份、revision/epoch；原生读取不能把旧提交当作新恢复。

冻结之后又回退时，Root 同一只读能力先保存已物理验证的部分推进，再从一致快照读取尚未恢复需求的真实来源变化。暂停、删除和明确整需求取消是用户控制，不产生来源变更修复事实；普通同一工作项的新 retry epoch 也不意味着新契约。真实 superseded/cancelled item、缺失、revision 倒退/变化或契约身份改变，不直接授权新 revision。管理事务重新读取同一变化及实际交还来源后保存 repair-runtime-cohort-changed 派生事实、当前 artifact 和完整基线，回到同一 Case 的新 Admin 调查轮；旧进展与独立通过收据保留，却无权关闭新来源。后续仍需实际修复/独立覆盖完整原目标/候选构建/外部切换/重新冻结当前真实链并观察普通推进，不是将状态直接完成。

这是明确的来源权限失效事实，不是 LLM 错误分类器，也不是新原始验收目标。requiredOriginalCoverage、管理提示和新的调查上下文明确区分它与全部原故障；可用派生事实的当前 artifact 实际定位源码。重复/过期/伪造为未变化的状态不能再声明一轮；STOP 不增加故障事实。若新一轮修复得到完全相同 sourceId，可复用既有真实构建候选，但必须重新执行当前轮独立验证与后续交还，不能把复用当作新来源已经通过。

空原工作集合也不是业务恢复证明。没有冻结 Work Item 时，Root 重新打开实际业务库并要求完整协议表、当前普通宿主精确 supervision token、正常非 crashed 生命周期、全部原观察及候选/交还来源后，保存 append-only `runtimeOriginalOperationReceipt`；有原 Work Item 时禁止用它代替普通执行推进。该收据仍不创建任务或完成 Dev/Test。

Root 的 runtime 观察现已调用与正常调度共用的生产 readonly 派发适配器，并把每条未恢复原需求的 runnable/waiting/executing 状态持久化到管理库。只有同一候选/交还/item revision/epoch 且新鲜相邻样本连续可派发 20 分钟才形成派生停滞事实；依赖、资源、全局并发、运行中长命令、暂停、STOP、断档和来源变化都会清零。非 Harness/更广泛构建前 runtime 诊断、真实模型的完整修复和整夜验收仍未完成。当前 Windows 观察路径拒绝缺失原生容器证明，不凭 ledger 放行。本节受控 SQL/宿主夹具通过仅证明协议门禁，不代替真实 Agent 修复效果。

## 交还后的派发停滞计时

业务工作项交还后的观察使用实际派发条件，而不是 display ready 或重复日志。纯领域策略 `repair-dispatch-watch` 仅累计相邻、新鲜、同一运行意图代次的 runnable 观察；120 秒以上断档或时钟回拨重置连续区间，不保留断档前累计时间来拼成 20 分钟停滞。短暂停机后及时续上观察仍保留历史；暂停、依赖/资源/全局槽位等待、正在执行的长命令以及来源变化都不累计。

达到 20 分钟后也不能永久获得接管权限：业务 hold 开始前、事务提交前及管理库写入故障时重新校验观察新鲜度、独立验证、交还来源和监督。异步能力等待过久后不允许依据过期观察暂停业务或创建修复故障，下一轮重新采样。观察计时不是完成证明，也不允许直接完成 Dev/Test。此策略目前接在已有业务交还能力；runtime 恢复集合仍需拆出可注入的只读实际派发依赖后接入，不能以该业务单元测试宣称 runtime 持久化停滞观察已经完成。

## 余下完整闭环

派发队列选择已抽为 `createDispatchQuery` 共享核心，普通 Runner 使用原 `dispatch-planner` 适配器注入协调、实际资源与图读取；固定 resume 协议目录由纯 `agent-command-profile-catalog` 提供，不通过 YAML/应用库初始化。核心运行时仅导入纯领域资源和优先级值，读图、容量、资源、依赖、服务观察均须显式注入。`inspectDispatchInDb` 禁用协调和 stale-claim 清理；需要 admission 却没有注入协调能力时明确拒绝，不能静默当成正确派发。

较早独立核心反例中的部分条件是夹具端口值，只证明核心隔离。现已提供 `dispatch-query-reader` 的完整实际查询适配器：复用普通业务的资源、进程屏障、容量、上下文会话、图和依赖函数，不加载 `database`、命令链配置、投影或 Web。原文档判定复用实际 artifact/result/frozen execution 校验；hash 和固定 profile 通过纯领域入口提供。旧业务模块重导出这些同一读取函数，避免复制两套规则。

`inspectDispatchReadonlyInDb` 只接受调用方拥有的 readonly 连接，在一致快照前后执行监督回调，不创建或迁移数据库，读取错误不变成空队列。业务交还能力已改用同一个 `inspectPersistedDispatchInDb` 读取入口，仍在业务方持有事务与连接，不向 Root 授予可写业务连接。独立编译子进程实际执行该生产适配器并读取非空图、实际资源 claim、前置需求和容量，故意损坏的 bootstrap 目标及输入 DB/WAL 字节不变，没有简化端口替代。正式发布产物的正反例还覆盖独立 readonly 连接上的冻结 publisher、applied result 和内容污染；人工阅读结卡仍保留。

这些图、完成收据和 allocation 是受控夹具，不是实际模型修复或 CLI 物理终止的证据。Root 原生观察能力已接入该入口，并保留完整版本/进程/代次校验及管理库持久化停滞观察；但不能仅据 SQL queue、ready 或计时判定整体 runtime 修复已经完成，也不能直接导入普通 `dispatch-planner`。

外部更新控制器必须独立于即将被替换的 Runner：取得监督与更新所有权，停止并确认冲突进程退出，在隔离区测试/构建，校验候选产物，切换并进行启动健康验证，失败时恢复已知可用版本。当前已接入受持久化租约与静默门禁保护的原生受管进程、阶段历史、独立实际数据库读者和专用生命周期激活入口，见 [外部运行版本更新](./external-runtime-update.md)。实际匹配版本切换及启动异常回滚证据见 [实施记录](./admin-recovery-implementation.md)；不是发行安装器或真实模型修复的替代。启动成功不是业务修复成功；还必须重跑原始失败与验收并观察正常工作项推进。

数据库版本兼容应在切换前确定；不得通过恢复旧数据库快照回滚已发生的业务写入。候选首次启动不得先自动恢复业务再判断兼容性。Windows 原生进程容器、三条真实模型业务闭环与 8–12 小时整夜验收也仍须完成。
